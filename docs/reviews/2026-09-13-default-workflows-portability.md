# Default workflow follow-up: portability and GUI acceptance

Date: 2026-09-13. Follow-up to [the initial GUI report](2026-09-13-default-workflows-gui.md).

## Release assessment

**The GUI coverage requirement is met: 19 independently accepted distinct tasks, with at least three for each of the six workflows. The application is not ready for release.** Windows restricted-token execution cannot run the unchanged npm/Node test runner when it needs piped child processes. Native Linux and macOS validation has not been performed on this machine. Backup planning still has documented false successes and missed mandatory requirements after consistency review.

The retained evidence contains 60 attempt or inspection records across 46 canonical runs and 763 recorded workflow calls. All GUI runs have settled. Counts must be read with the individual verdicts; a green application status, a passing external artifact test, or an accepted intermediate milestone alone is insufficient. This iterative exercise establishes the listed task outcomes, not a production reliability rate.

## Method and scope

The working tree already contained substantial changes. They were preserved. The original 18 Node project scenarios and their requirements remain in [gui-scenarios.mjs](../../benchmark/default-workflows/gui-scenarios.mjs), alongside portable-backup and portable-settings planning scenarios. Both additional requests were frozen before launch. The backup request explicitly covers all three operating systems, injected failure tests, retention after failed writes and bounded power-loss claims; its failed attempts remain unaccepted. The settings task adds read-only configuration precedence, strict validation, caller compatibility and host-supplied portable paths. A second suite of ten [Python maintenance-ticket tasks](../../benchmark/default-workflows/gui-python-scenarios.mjs) exercises different changes, bug reproductions and dependent integrations with an explicitly frozen Python unittest gate. Its additional Unicode search and reporting integration request was also frozen before launch. These are additional small synthetic product repositories, not replacements for npm requirements or evidence of production reliability.

All counted task runs select a workflow, enter the frozen request, launch, supervise, answer legitimate clarification and inspect outputs through headed Electron/Playwright controls. They use the saved standard route, OpenRouter `z-ai/glm-5.3-flash`. Application settings and credentials are copied to separate temporary profiles; credentials are outside retained evidence. No sandbox approvals were granted. No direct kernel launches, scripted providers or external artifact checks count as GUI completion.

Each attempt retains its request, settings/model labels, visible observations, screenshots, final output, canonical session, source workspace, independent checks, timings and provider-call counts under `.flyt/gui-workflows/2026-09-13-portable-*`. Earlier failed attempts are retained. Source and schema fixes landed between attempts; this is an iterative diagnosis, not a controlled before/after benchmark. [The summary script](../../scripts/summarize-default-workflow-gui.mjs) extracts actual root outputs and command receipts from those sessions.

Continuations and explicit fresh rechecks can share a working directory. Historical claims are bound to the saved session and content-addressed workflow evidence at the recorded digest, rather than assuming that directory still has the old contents. The harness selects retained runs by canonical ID; summary extraction also reads the ID from a frozen session for older attempts that lacked it in their manifest.

## Implemented fixes

- Planning has a separate bounded consistency review of interfaces, examples, failure ordering and stakeholder decisions. Actual clarification answers cross the review/repair boundary. Unresolved decisions remain drafts; exhausted contradictions fail with the draft retained. A reviewed specification is explicitly unimplemented and untested.
- Research quotation correction replaces only invalid source indexes, using already observed excerpts. An explicit replacement flag prevents a model's literal `null` string from erasing the useful answer. Valid sources are retained. Exact quotation validation remains mandatory.
- Stage output displays the validated structured completion, including formatting correction, instead of a preceding prose fragment. Review contracts separate actual introduced defects from optional test suggestions and reject contradictory passing reviews with findings.
- Reviews use stable criterion IDs resolved back to the original requirement text. A malformed review receives bounded reader-only correction, and invalid cached review rows can be regenerated on Retry. This avoids redoing correct implementation merely to fix bookkeeping. Intermediate reviews are scoped to their milestone; full-request acceptance is checked during integration, with historical milestone receipts bound to their original source versions.
- Resume compares the current source digest with the last accepted checkpoint or durable tool-effect observation. An interrupted worker's own recorded edits can resume; subsequent external edits fail before another model call. Accepted commands are retained and rerun during final integration, even without configured project gates.
- Generated stages participate in cooperative Pause at stage and verification-command boundaries. Continue revalidates the checkpoint before another call. Pauses and retries retain the original elapsed-time and call budgets.
- Optional recap failures use a compact expandable notice and retain the authoritative result. Resume and Retry refresh the recap; older recaps remain as superseded history. Projection clears the previous attempt's error when execution resumes and rebuilds degraded recaps from the current authored root result, including when older completed runs are reopened.
- Retry can recover a completed but malformed structured candidate, including a nested review correction, without repeating the finished worker or reader. Schema and source checks still apply. Exact quotations assigned to the wrong line can be relocated only when the unchanged text has one matching location in the same file; the canonical log records both line numbers.
- The Windows gate preflight supports App Execution Aliases and quoted executable paths. Unix discovery requires executable regular files. Shell guidance and GUI paths use the actual platform, and the worker's existing reasoning-effort setting is now honored.
- GUI screenshot capture retries and records failures instead of abandoning a live run on a transient capture error. Viewport screenshots retain the final output without relying on extremely tall captures. The harness can pause and resume through visible controls after an accepted milestone.

## Platform result

The filesystem probe now separately records Node piped-child support. On this Windows machine, confined Python unittest commands execute, but Node's pipe-creating child launch fails with `spawn EPERM`. A recorded command failure matching the failed capability probe ends verification rather than spending further implementation repairs on the same infrastructure limitation.

Diagnostics found that a newly created named pipe did not inherit the private restricting capability in the process token's default DACL. The pipe allowed the ordinary user full access and broad read access, but a restricted child lacked the write/control rights required to connect. Microsoft's [named-pipe access documentation](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights) and [libuv's Windows pipe implementation](https://github.com/libuv/libuv/blob/v1.x/src/win/pipe.c) explain the relevant defaults and access requests. Local observations are retained in `.flyt/pipe-diagnostic-result.log`; they are specific to the tested backend and runtime.

No broad user-SID capability, global pipe access, inherited unsandboxed execution or relaxed workspace ACL was introduced. Outside-workspace denial, private temporary directories, read-only restrictions and descendant termination remain tested.

The installed Windows Python execution alias was checked separately under the same restricted-token world. Python and its child process wrote inside the fixture workspace and were denied outside writes; cancelling a started Python descendant prevented a later inside-workspace sentinel write. No escalation occurred (`.flyt/python-confinement-result.log`). An initial diagnostic put its AbortSignal in the wrong options field and therefore did not test cancellation; that harness error is retained in `.flyt/python-confinement-invalid-harness.log`, and the corrected check passed without changing the backend.

With `FLYT_RELEASE_SANDBOX_E2E=1`, the platform suite now requires the unchanged npm/Node runner to pass. The current result is **six passed, one failed, zero skipped**: the failure is the explicit release compatibility gate. Ordinary diagnostic testing can successfully establish that a capability is unavailable; that cannot certify release compatibility. The Electron probe uses the installed native executable on all three operating systems.

The local Ubuntu and Debian WSL installations are WSL1 and have no working native Node/Bubblewrap test environment. They cannot certify the Linux execution backend. No macOS host was available. The repository's native OS release matrix remains the place to establish those results; neither platform is claimed verified here.

This verifies continuation without duplicate implementation. Pause is cooperative: it waited for the current multi-call stage to finish, rather than interrupting its tools immediately. The fixed integration receipt handoff was added after this run launched; its older reviewer caveat about unavailable intermediate receipts is retained in the evidence.

Passing status alone did not qualify them. Corrected reruns preserve these failures and the later independent decisions.

The backup and finance plans also exhausted their original time allowances in earlier attempts. The harness now distinguishes a newly settled attempt from an old Failed display. Fresh reruns use the same requests with concise specification guidance, without raising their budgets. Provider stalls, overly long reasoning and correction overhead remain practical latency concerns.

The later validation run exposed a provider response that ignored forced structured submission and repeated end markers instead. That attempt was stopped through the GUI, preserving code and progress. This narrows routing to compatible endpoints; it does not guarantee model compliance, and malformed results still fail. See [OpenRouter's parameter-support contract](https://openrouter.ai/docs/guides/routing/provider-selection). Both correction and repeated-failure recovery are covered by the **48 passing workflow tests** in `.flyt/defaults-review-consistency-tests.log`. No boolean is changed automatically.

Specification reviews also now default to 8,192 output tokens and concise focused checking, without extending their 20-minute deadline.

The host's empty before/after change correctly rejected that claim. Workers now receive the precise baseline meaning and previously observed paths; an inconsistent completion report gets one visible reader-only correction against the host snapshot. It cannot edit files, run commands or bypass the independent acceptance review. This avoids cosmetic edits and preserves the distinction between implementation and already-satisfied work. The workflow and failure-recovery suites passed **57 tests**, zero failed/skipped, including both saved-candidate and legacy recovery (`.flyt/defaults-format-recovery-tests.log`).

The second formatter failure had about 81 seconds without a new chunk before timeout; the first included a roughly 76-second gap. The runtime can now locate an unchanged quotation when exactly one line location matches in that file, recording both requested and verified lines. Missing and ambiguous quotations remain rejected. These changes preserve acceptance checks rather than interpreting positive prose as success.
